# Generation Procedure — Factory Algorithm

End-to-end algorithm the factory follows when generating a project's component skill.

---

## Inputs

- A workspace (the user's project)
- Optional user-provided project name / stack overrides
- Optional re-run flag (when an existing generated skill is detected)

## Outputs

- `<skills-path>/<project>-component-library/SKILL.md` (skills-path inferred from design-system skill location, default `.github/skills/`)
- `<skills-path>/<project>-component-library/references/component-rules.md` (universal principles — one file, all stacks)
- `<skills-path>/<project>-component-library/references/<stack>.md` (one file **per detected stack** — conventions, file tree, tool notes)
- Idempotent append to the project's **primary agent instruction file** (resolved from `<skills-path>`) and any existing secondary files
- A summary printed to the user

---

## Algorithm

### Step A — Detect

Load [project-detection.md](./project-detection.md). Fill in every category in the **Detected Project Context** block. Each value is either:
- A detected value with source (`Riverpod (pubspec.yaml)`)
- `not detected` (e.g., no animation library)
- `inferred — please confirm` (used only when reasoning from a weak signal)

### Step B — Check for an existing generated skill

```
<skills-path>/<project>-component-library/SKILL.md
```

**If it exists:** read the trace comment `<!-- Generated by create-component-library-skill vX.Y on YYYY-MM-DD ... -->` and show its version + date + stack. Then:

1. **Integrity check.** Verify `references/component-rules.md` exists and is non-empty, and that a `references/<stack>.md` exists for each stack listed in the trace comment. If any file is missing or truncated, treat the skill as broken — offer **Repair** (regenerate all files) or **Cancel**.
2. **Local-edit check.** Run `git status --porcelain <skills-path>/<project>-component-library/`. If any file shows as modified (`M`) or untracked since the trace date, warn:
   > ⚠️ Local changes detected in `<project>-component-library/` since it was generated on YYYY-MM-DD. Regenerating will discard them. Commit or stash first.
3. **Version check.** If the trace version is older than this factory's version (`v1.0`), surface: "Generated by an older factory version (vX.Y). A regenerate will upgrade to current rules."
4. **Ask the user:**
   - **Regenerate from scratch** — overwrite all generated files (SKILL.md, component-rules.md, all stack reference files)
   - **Skip** — leave files as they are; only re-run agent instruction update if needed
   - **Cancel** — abort

**Never silently overwrite.** Never attempt a 3-way merge.

### Step C — Confirm context

Print the Detected Project Context block. Ask:

> Proceed with these conventions? Type any corrections (e.g., "use kebab-case", "components live in `src/widgets/`"), or confirm to continue.

Required for any line marked `inferred — please confirm`. Optional otherwise but recommended.

### Step D — Load source material

Read into context:
- `principles/component-anatomy.md`
- `principles/state-modeling.md`
- `principles/token-integration.md`
- `principles/models-and-stubs.md`
- `principles/preview-catalog.md`
- `principles/testing-strategy.md`
- `generated-skill-template.md`
- `generated-rules-template.md`
- `generated-stack-reference-template.md`
- `output-spec.md`

> Note: `principles/accessibility-rules.md` is **not inlined** into the generated output. The §6 Accessibility section in `generated-rules-template.md` uses a fixed delegate block pointing to the standalone `accessibility` skill. No need to read the file during generation.

### Step E — Render SKILL.md

Use `generated-skill-template.md`. Substitute:
- `{{project-name}}` — the resolved project slug (lowercase-hyphenated)
- `{{project-display}}` — display name (e.g., "Acme")
- `{{stack}}` — detected stack name(s)
- `{{detected-context-table}}` — project-wide summary table: stacks, design-system skill, atomic-UI skill (per-stack details live in the stack reference files)
- `{{stack-routing-table}}` — routing table from context signals to stack reference links. Single-stack: one row. Multi-stack: one row per stack using the signal/filename conventions in `generated-stack-reference-template.md`.
- `{{design-system-clause}}` — paragraph referencing the design-system skill, OR the "no design-system detected" hint
- `{{atomic-ui-clause}}` — always present: "This skill is invoked per-component by the `atomic-ui` skill during screen decomposition. Build atoms first, compose up to molecules and organisms." (The `atomic-ui` skill is always available as part of the gen-e2-design plugin — no detection needed.)
- `{{trace-comment}}` — `<!-- Generated by create-component-library-skill v1.0 on YYYY-MM-DD. Stack: X. Design-system: Y. -->`

Validate: no unresolved `{{...}}` placeholders.

### Step F — Render component-rules.md

Use `generated-rules-template.md`. For each principle section, inline the content from `principles/<file>.md` with these substitutions:
- Replace references to "the loaded platform guide" / "your platform guide" with the detected stack name where appropriate
- In the **Design Tokens** section:
  - If no design-system skill detected, set `{{tokens-prerequisite-notice}}` to a prominent `> ⚠️ No design-system skill installed` callout (see `generated-rules-template.md` substitution reference). Otherwise set to empty string.
  - Append a project subsection: either "Tokens for this project come from `.github/skills/<design-name>-design-system/`" with concrete file pointers, or the "no design-system skill detected — using platform default theme" notice with a hint to run `create-design-system-skill`
- The **§2 Project Conventions** section is a fixed delegate note (no table). The **§10 File Structure** section is a fixed delegate note (no tree). Both point to the stack reference file(s) — write them exactly as shown in `generated-rules-template.md`.
- The **Accessibility** section is **not inlined from any principle file** — write the fixed delegate block exactly as shown in `generated-rules-template.md` §6
- **§8 Previews** and **§9 Testing** include the full inlined principle content but no tool/framework pointer lines — those live in the stack reference file

Validate: no unresolved placeholders; file size within 1000–1400 line budget.

### Step F2 — Render stack reference file(s)

For each detected stack, use `generated-stack-reference-template.md`. Substitute all `{{...}}` placeholders for that stack:
- `{{stack}}`, `{{stack-display}}`, `{{project-display}}`
- `{{component-dir}}`, `{{naming}}`, file-pattern placeholders
- `{{state-mgmt}}`, `{{test-framework}}`, `{{preview-tool}}`, `{{animation-lib}}`, `{{i18n-lib}}`, `{{design-system-skill}}`
- `{{component-tree-example}}` — concrete file tree for `MetricCard` using this stack's detected conventions
- `{{test-location}}` — concrete test path for `MetricCard`
- `{{preview-tool-pointer}}` — file naming pattern + launch/run command for the confirmed preview tool.
  - **Flutter (Flutter Widget Previewer — default):** the pointer MUST cover:
    - Co-located preview files: `<component>_preview.dart` in the component's own folder.
    - A shared `ComponentPreview` helper annotation that extends `Preview` (from `package:flutter/widget_previews.dart`), defaults to a **mobile** `Size`, and carries shared theme / `wrapper` / localization defaults. It lives in a top-level module folder — `lib/preview/component_preview.dart` (sibling to `lib/core/`) — so components import it via a package import.
    - Use `@Preview` for single previews and `MultiPreview` for state/config matrices; annotate top-level functions, static methods, or no-arg constructors.
    - Group variations with the `group` parameter using the label format `"<Component> / <State>"` so each state's config variants (light/dark, 2× text, RTL, narrow) cluster under one group instead of rendering as separate top-level previews.
    - Inject theme/locale/a11y via the `wrapper` parameter; feed data from **shared model stubs** only — never inline or live data.
    - Run with `flutter widget-preview start` (or the "Flutter Widget Preview" tab in VS Code / Android Studio). No `build_runner` / codegen step is required — the previewer generates its own.
    - Note the requirement: Flutter 3.35+ (IDE support 3.38+); the API is experimental.
  - **Flutter (Widgetbook — brownfield only):** emit Widgetbook pointer guidance **if and only if** Widgetbook dependencies were already present **and** the user explicitly confirmed keeping it (the ask is mandatory even when detected). In every other case — greenfield, no Widgetbook present, no confirmation, or an ambiguous answer — use the Flutter Widget Previewer guidance above; never introduce Widgetbook into a project that doesn't already have it. When kept, reference `@UseCase` entries + the `build_runner` codegen step.
- `{{test-framework-pointer}}` — query priority guidance + run command for the detected test framework

Validate: no unresolved placeholders; file size 30–70 lines per file.

### Step G — Write the files

Resolve `<skills-path>`: if a design-system skill was found in step A, use its parent directory (e.g., `.claude/skills/` or `.github/skills/`). Otherwise default to `.github/skills/`.

```
<skills-path>/<project>-component-library/SKILL.md
<skills-path>/<project>-component-library/references/component-rules.md
<skills-path>/<project>-component-library/references/<stack>.md   (one per detected stack)
```

**Atomic write order:**
1. Create the directory and `references/` subdirectory.
2. Write `references/component-rules.md` first. On failure, abort — do not write anything else.
3. Write each `references/<stack>.md` in sequence. On any failure, delete all files written so far and abort.
4. Write `SKILL.md` last (the dispatcher). On failure, delete all previously written files and abort.
5. On any failure, **do not proceed to Step H** (agent instruction update). Print a clear error showing which write failed.

This order guarantees a partial failure never leaves a dispatcher pointing at missing references.

### Step H — Update agent instruction files (idempotent)

#### H1 — Resolve the instruction file target set from the skills-path ecosystem

The `<skills-path>` already signals which agent ecosystem the project uses. Derive the primary instruction file from it; do not blindly iterate over a fixed list.

| `<skills-path>` | Primary instruction file | Secondary (append-only, only if they already exist) |
|---|---|---|
| `.github/skills/` | `copilot-instructions.md` | `.github/instructions/*.instructions.md` |
| `.claude/skills/` | `CLAUDE.md` | `AGENTS.md` |
| anything else | `AGENTS.md` | `copilot-instructions.md`, `CLAUDE.md` |

**Build the target set:**
1. Check whether the **primary** file exists.
2. Check whether any **secondary** files exist.
3. Determine targets:
   - If primary exists → include it in the target set
   - If primary does NOT exist AND at least one secondary exists → use only the existing secondary files; do not create the primary
   - If primary does NOT exist AND no secondary files exist → create the primary file (append the trigger line; no other content is generated)
4. Include any existing secondary files in the target set alongside the primary.

#### H2 — Apply the trigger line to each target file

Construct the exact line:
```
Before creating, refactoring, or reviewing any UI component, load the `<project>-component-library` skill.
```

For each file in the target set, perform two checks:

1. **Match this skill's name (idempotent):** grep for the literal line above (with this run's `<project>` value). If present → skip.
2. **Match a prior name for the same role (cleanup):** grep with the regex `^Before creating, refactoring, or reviewing any UI component, load the \`[a-z0-9-]+-component-library\` skill\.$`. If a match exists with a *different* skill name (project was renamed), surface the stale line to the user and ask: **Replace** (delete old, append new) / **Keep both** / **Skip**. Never silently leave conflicting lines.
3. **Code-fence guard:** when grepping, ignore lines inside fenced code blocks (lines between a pair of ```` ``` ````). Documentation snippets must not count as matches.

If neither check finds a match → append the line to the end of the file, preceded by a blank line if the file doesn't already end with one.

Never edit existing non-trigger lines. Never restructure the file.

### Step I — Self-audit

Run the self-audit checklist from `output-spec.md`. Fix any failures **before** reporting completion.

### Step J — Print summary

```
✓ Generated component skill for <project>

Files written:
  <skills-path>/<project>-component-library/SKILL.md            (~130 lines)
  <skills-path>/<project>-component-library/references/component-rules.md  (~[size] lines)
  <skills-path>/<project>-component-library/references/<stack>.md           (~50 lines)
  [additional stack references for each extra stack]

Agent instructions updated:
  <primary-instruction-file> — appended trigger line (or: already present, skipped)
  [any secondary files that existed — listed here]

Detected context:
  Stacks: Flutter | Design system: acme-design-system | Atomic UI: not detected
  (Per-stack details: see references/<stack>.md)

Next steps:
  • The new skill is auto-loaded when you ask to build, refactor, or review components.
  • To regenerate after convention changes, re-invoke the create-component-library-skill.
  • Hand-edits to the generated files persist until the next regeneration (commit first).
  [Only if user chose a preview tool not yet installed]
  • Preview tool setup: <install-hint from project-detection.md §6 stack-idiomatic defaults>
```

## Overwrite Policy (Summary)

| Target | Policy |
|---|---|
| `<skills-path>/<project>-component-library/SKILL.md` | Ask before overwrite (Step B) |
| `<skills-path>/<project>-component-library/references/component-rules.md` | Overwritten alongside SKILL.md when user chooses Regenerate |
| `<skills-path>/<project>-component-library/references/<stack>.md` | One file per detected stack — overwritten alongside SKILL.md when user chooses Regenerate; new stack file added without prompting if it doesn't exist yet |
| Primary agent instruction file (resolved from skills-path) | Idempotent append; created if nothing else exists |
| Secondary agent instruction files (if they exist) | Idempotent append only, never create, never edit existing content |
| Any other file | Never touched |

## Multi-Stack (Monorepo)

Multi-stack projects use a **single** `<project>-component-library` folder. Universal principles in `component-rules.md` apply to all stacks. When multiple stacks are detected, repeat Steps F2 and G (the stack reference writes only) **per stack**, adding a new `references/<stack>.md` to the same `references/` folder.

The SKILL.md `## Stack References` routing table (the `{{stack-routing-table}}` placeholder) must include one row per stack. SKILL.md is written **once** — it routes to all stack reference files.

When adding a new stack to an existing project (re-run that adds a stack):
1. Follow the Step B overwrite flow for SKILL.md (regenerate to update the routing table, or skip).
2. Check whether `references/<new-stack>.md` already exists — if not, generate and write it. If it does, offer the same regenerate/skip/cancel choice.
3. `component-rules.md` rarely needs regeneration when adding a stack — universal principles are unchanged.
4. Update agent instruction files only if the trigger line is missing (idempotent append; the line is the same regardless of stack count). The target set is resolved from the skills-path per Step H.

## Failure Modes

| Failure | Handling |
|---|---|
| Project name cannot be derived | Ask user once; refuse to invent one |
| No stack detectable AND no design-system skill | Ask user; if still unknown, proceed with generic principles and mark the Stack row `unknown — please specify` |
| `.github/skills/` write blocked | Surface the error; do not attempt workarounds |
| Existing skill detected, user chooses Cancel | Exit cleanly, no files touched |
